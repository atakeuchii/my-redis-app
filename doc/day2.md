# Day 2: Redis における原子性の保証範囲と、その外側で起きること

在庫管理・レートリミッタ・ジョブキューの 3 題材を通じて、
Redis が原子性をどこまで保証するか、その境界を越えたときに何が壊れるかを計測した。

---

## 1. 目的

Redis は「シングルスレッドだから安全」と説明されることが多い。
しかしこの説明は保証の範囲を明示しておらず、誤用を招きやすい。

本実験では次の 3 点を明らかにする。

1. Redis が原子性を保証する単位はどこまでか
2. その境界を越えた使い方をしたとき、具体的にどのような壊れ方をするか
3. Redis が原子性を保つために用意している仕組みと、それでも不足する場合の対処

---

## 2. 実験環境

Day 1 と同一。PostgreSQL 16（5437 番）、my-redis（6380 番）、Redis 公式（6379 番）。
題材は架空のゲームの限定アイテム（在庫 5〜50 個）を用いた。

同時アクセスは 20 スレッド、ジョブキューは 5 ワーカーで計測した。

---

## 3. Redis が原子性を保証する範囲

### 3.1 保証の単位はコマンド 1 個

Redis はコマンドの実行を単一スレッドに直列化している。
したがって **1 つのコマンドの実行中に、他のコマンドが割り込むことはない**。

この性質により、以下は追加の同期機構なしに安全である。

```
INCR counter        # 読み取りと加算の間に割り込まれない
SET k v NX          # 存在確認とセットの間に割り込まれない
RPOPLPUSH a b       # 取り出しと追加の間に割り込まれない
```

逆に、**複数のコマンドにまたがる操作は一切保証されない**。
これが本実験で繰り返し観測された壊れ方の原因である。

### 3.2 Redis が用意している「まとめる」仕組み

Redis には、よく使われる複合操作を 1 コマンドにまとめた命令が多数存在する。

| 素朴な 2 コマンド | 原子的な 1 コマンド |
|---|---|
| `GET` → 判定 → `SET` | `INCR` / `DECR` / `INCRBY` |
| `EXISTS` → `SET` | `SET ... NX` |
| `SET` → `EXPIRE` | `SET ... NX EX` |
| `RPOP` → `LPUSH` | `RPOPLPUSH` |
| `GET` → `SET` | `GETSET` |

これらは「あると便利」ではなく、**それが無いと正しく書けない**という性質のものである。
Redis の初期実装が `LPUSH` + `LTRIM` という用途から出発したことを踏まえると、
コマンドセットは「用途から逆算して原子的な単位を切り出した結果」と理解できる。

### 3.3 Lua スクリプト

複数キーをまたぐ操作や、条件分岐を含む複合操作は、既存のコマンドでは表現できない。
Redis はこれに対して `EVAL` による Lua スクリプトを提供している。

スクリプトは**実行スレッド上で、他のコマンドを挟まずに実行される**。
すなわち「任意の処理を 1 コマンドに昇格させる」仕組みである。

本実験で用いた自作実装には Lua が未実装であるため、
この層が必要になる場面では解決不能であることを確認するに留まった。

## 4. 境界を越えたときの壊れ方

### 4.1 在庫: read-modify-write

#### 素朴な実装

```clojure
(let [current (stock item-id)]        ; ① 読む
  (if (pos? current)
    (do (set-stock! item-id (dec current))   ; ② 書く
        :ok)
    :sold-out))
```

在庫 20 個に対し 20 スレッドから 200 回の購入を試行した。

| 実装 | 結果 |
|---|---|
| DB（`SELECT` → `UPDATE`） | **成功回数が 20 を超過、在庫がマイナス** |
| Redis（`GET` → `SET`） | **同上** |

**Redis を用いても、使い方が素朴であれば DB と同じように壊れる。**
「Redis だから安全」という理解が誤りであることを示す結果である。

#### 原子的な実装

| 実装 | 正しさ | 1 回 | スループット |
|---|---|---|---|
| SQL `UPDATE ... WHERE stock > 0` | 正しい | 2.092 ms | 584 回/秒 |
| Redis `DECR` | 正しい | 0.582 ms | **5363 回/秒** |
| Redis `DECR`（本物） | 正しい | — | 3733 回/秒 |

SQL も条件を `WHERE` に含めることで 1 文に収まり、行ロックにより直列化されるため正しい。
正しさの観点では両者に差はなく、**差があるのは速度である（9.2 倍）**。

なお、20 スレッドに増やしても SQL のスループットは 1.2 倍にしかならなかった
（1 スレッド 2.092 ms に対し、20 スレッドで 1.712 ms/回）。
同一行への更新は行ロックで直列化されるため、並列度を上げても効果がない。

#### `DECR` でも足りない点

`DECR` は原子的だが、**「0 未満にしない」という条件を表現できない**。

在庫 20 に対し 200 回の `DECR` を行うと、最終在庫は −180 となる。
売り過ぎ（成功判定）は防げるが、在庫値そのものが壊れる。
補充時に `INCRBY 50` しても −130 のままとなり、在庫が復活しない。

補償（`DECR` してマイナスなら `INCR` で戻す）により最終値は正しくなるが、
以下の 2 点は解決しない。

- `DECR` と `INCR` の間に一瞬マイナスが見える
- 補償の前にプロセスが落ちると、マイナスのまま残る

### 4.2 レートリミッタ: `INCR` と `EXPIRE` の分離

#### 素朴な実装

```clojure
(let [n (r/cmd pool "INCR" k)]
  (when (= n 1)
    (r/cmd pool "EXPIRE" k window))    ; ← ここに到達する前に落ちると
  (<= n limit))
```

`INCR` の直後にプロセスが落ちる状況を再現したところ、
キーは値 1、TTL は −1（期限なし）の状態で残った。

以降このユーザーは制限に達した後、**TTL が無いため永久にブロックされる**。
手動で `DEL` しない限り回復しない。

#### 原子的な実装

```clojure
(if (= "OK" (r/cmd pool "SET" k 1 "NX" "EX" window))
  true                                  ; 初回。TTL 付きで作られる
  (<= (r/cmd pool "INCR" k) limit))     ; 2 回目以降。TTL は既に付いている
```

`SET NX EX` は「存在しなければ値と TTL を同時にセットする」を 1 コマンドで行う。
どの時点で落ちても、キーが存在すれば必ず TTL が付いている状態になる。

並行テスト（20 スレッド × 5 回 = 100 回、上限 10）の結果は **10 回通過** で正しい。

#### 固定ウィンドウの境界問題

`SET NX EX` 方式は原子性を保つが、**別種の問題を持つ**。

ウィンドウが時刻に固定されているため、切れ目の前後で上限の 2 倍が通過しうる。

```
00:00〜00:59 に 10 回  ← OK
01:00 にキーが失効
01:00〜01:01 に 10 回  ← OK
→ 実質 2 秒間に 20 回通過
```

#### スライディングウィンドウ

ZSet にタイムスタンプを記録し、常に「現在から window 秒前まで」を見る方式で
境界問題は解消する。ただし処理が 4 コマンドに分かれる。

```
ZRANGEBYSCORE + ZREM  （ウィンドウ外を削除）
ZCARD                  （現在数を取得）
ZADD                   （今回を記録）
EXPIRE
```

並行テスト（100 回、上限 10）の結果は **19 回通過** となり、原子性が失われた。
`ZCARD` で数えてから `ZADD` するまでの間に、他スレッドが割り込んでいる。

#### 結果の対称性

| 方式 | 境界問題 | 原子性 | 100 回中の通過数 |
|---|---|---|---|
| 固定ウィンドウ | **あり**（約 800 ms で 19 回） | 保たれる | 10 |
| スライディング | 無し | **壊れる** | **19** |

両者が同程度の超過を示したのは偶然だが、
**時間の境界と並行性の境界という異なる原因が、同じ帰結をもたらす**ことを示している。

両方を満たすには Lua による 1 コマンド化が必要であり、本実験の自作実装では達成できなかった。

### 4.3 ジョブキュー: `RPOP` と `LPUSH` の分離

#### 素朴な実装

`RPOP` で取り出すと、ジョブは Redis から消える。
処理中にワーカーが落ちた場合、ジョブはどこにも残らない。

失敗率 20% で 100 件を処理したところ、**約 20 件が消失**した。

#### 2 段階方式

`RPOP` の後に処理中リストへ `LPUSH` することで、失敗したジョブを復元可能にした。

失敗率 20% での結果：消失 0 件、処理中リストに 20 件が残留。

ただし **`RPOP` と `LPUSH` の間で落ちると、やはり消失する**。
この隙間でクラッシュさせたところ、**100 件すべてが消失**した。

#### `RPOPLPUSH`

本物の Redis には、この 2 操作を原子的に行うコマンドが存在する。

```
RPOPLPUSH source destination
```

どの時点で落ちても、ジョブは source か destination のいずれかに必ず存在する。
「その間」という状態が存在しない。

#### 自作実装での代替

`RPOPLPUSH` が無い場合、**順序を逆にする**ことで消失を防げる。

```clojure
(let [job (r/cmd pool "LINDEX" queue-key -1)]   ; 覗くだけ（消さない）
  (r/cmd pool "LPUSH" processing-key job)
  (r/cmd pool "RPOP" queue-key))
```

隙間で落ちても消失しないが、**両方のリストに存在する状態（重複）が生じうる**。

| 方式 | 消失 | 重複 | コマンド数 |
|---|---|---|---|
| `RPOP` のみ | **あり** | 無し | 1 |
| `RPOP` → `LPUSH` | **あり**（隙間） | 無し | 2 |
| `LINDEX` → `LPUSH` → `RPOP` | 無し | **あり** | 3 |
| `RPOPLPUSH` | 無し | 無し | 1 |

## 5. 考察

### 5.1 4 つの事例は同一の構造を持つ

| 題材 | 分離していた 2 操作 |
|---|---|
| 在庫 | 読む → 判断して書く |
| レートリミッタ（固定） | `INCR` → `EXPIRE` |
| レートリミッタ（スライディング） | `ZCARD` → `ZADD` |
| ジョブキュー | `RPOP` → `LPUSH` |

いずれも「判断あるいは第一の操作」と「実行あるいは第二の操作」が
別コマンドに分かれており、その間に他のクライアントが割り込める。

**Redis の原子性はコマンド境界で切れる。** これが本実験の中心的な結論である。

### 5.2 Redis の設計は「用途を 1 コマンドに畳む」方向に進化している

`INCR`、`SET NX EX`、`RPOPLPUSH`、`GETSET`、`LTRIM` ——
これらは単なる糖衣構文ではなく、**それが無ければ正しく書けない操作**である。

Redis が「データ構造サーバ」を自称し、値の型を知った上で操作を提供しているのは、
この原子的な単位を切り出すためと理解できる。
単なる KV ストアであれば、すべての複合操作がクライアント側の read-modify-write になり、
本実験で観測したすべての問題が常時発生することになる。

Lua スクリプトは、この方向性の論理的な帰結である。
「用途ごとにコマンドを追加する」ことには限界があるため、
**任意の処理を 1 コマンドに昇格させる汎用機構**を用意した、と位置づけられる。

### 5.3 原子的なコマンドが存在しても、表現力は有限

`DECR` は原子的だが「0 未満にしない」を表現できない。
これは「原子性があれば正しい」わけではないことを示す。

対処は 3 通りある。

| 方針 | 利点 | 欠点 |
|---|---|---|
| 補償（減らして戻す） | 既存コマンドのみ | 一瞬不正な値が見える、補償前の障害で破綻 |
| Lua で条件分岐ごと原子化 | 完全 | Lua が必要 |
| 設計を変える（別のデータ構造を使う） | 場合による | 用途依存 |

本実験では補償方式を実装し、最終値は正しくなるが
**中間状態の可視性と障害時の残留という 2 つの副作用**が残ることを確認した。

### 5.4 消失と重複は交換可能である

ジョブキューにおいて、`RPOPLPUSH` が使えない場合の選択は
**「消失を許すか、重複を許すか」**になる。

2 つの操作の順序を入れ替えるだけで、どちらを許容するかが決まる。

```
消す → 入れる   → 隙間で落ちると消失
入れる → 消す   → 隙間で落ちると重複
```

これは分散システムにおける at-most-once / at-least-once の選択と同型である。
**exactly-once は 1 コマンドに収めるか、外部の仕組みに頼る以外に実現できない。**

実務上は、ジョブが冪等であれば重複を許す設計が安全側となる。

### 5.5 読み取りと書き込みで Redis の優位性が逆転する

Day 1 のプロフィール取得では DB と Redis の差は 1.4 倍に留まったが、
本実験の在庫更新では 9.2 倍の差が生じた。

| | Day 1（読み取り） | Day 2（競合する書き込み） |
|---|---|---|
| DB 側のコスト | インデックス検索 0.05 ms | 行ロック + MVCC + WAL + fsync |
| 支配的要因 | TCP 往復 | **ディスク同期書き込み** |
| DB vs Redis | ほぼ同等 | 9.2 倍 |

PostgreSQL の `UPDATE` は、新しい行バージョンの作成、WAL への書き込み、
コミット時の fsync を伴う。これは自作 Redis の `appendfsync always` が
2.99 ms を要したのと同種のコストである。

Redis が AOF を無効にしていれば、`DECR` はメモリ上の整数操作のみで完結する。

**「Redis は速い」が成立するのは、永続化を伴わない書き込みの場合である。**
AOF を `always` にすれば、この優位は大きく失われると予想される。

### 5.6 「Redis は単一スレッドだから安全」という説明の危険性

この説明は正しいが、保証範囲を明示していないため誤用を招く。

本実験では、Redis を用いた素朴な実装（`GET` → `SET`）が
DB の素朴な実装とまったく同様に壊れることを確認した。

正確には次のように述べるべきである。

> Redis はコマンド 1 個の実行を直列化する。
> 複数コマンドにまたがる操作の原子性は保証しない。

---

## 6. 結論

1. **Redis の原子性はコマンド 1 個の単位で成立する。**
   複数コマンドにまたがる操作は、DB の read-modify-write とまったく同じ形で壊れる。

2. **Redis は「よく使う複合操作を 1 コマンドに畳む」方向でこれに対処している。**
   `INCR`、`SET NX EX`、`RPOPLPUSH` 等は利便性ではなく正しさのために存在する。
   Lua スクリプトは、この方向性を任意の処理に一般化した機構である。

3. **原子的なコマンドが存在しても、表現力の不足から壊れる場合がある。**
   `DECR` は「0 未満にしない」を表現できず、補償方式では中間状態の可視性と
   障害時の残留という副作用が残る。

4. **1 コマンドに収まらない要求は、何かを諦めるか Lua に頼るしかない。**
   レートリミッタでは「境界問題」と「原子性」のいずれかを、
   ジョブキューでは「消失」と「重複」のいずれかを選ぶことになる。

5. **競合する書き込みにおいて、Redis は DB に対し 9.2 倍の優位を示した。**
   ただしこれは永続化を伴わない場合の値であり、
   読み取りのみの Day 1 では差がほとんど生じなかったことと対照的である。

6. **実装上の指針**
   - 複数コマンドを使う箇所を見つけたら、原子的な代替コマンドの有無を確認する
   - 無ければ Lua を検討する
   - いずれも不可能なら、**何を諦めるかを明示的に選ぶ**（消失か重複か、厳密さか単純さか）

---

## 7. 本実験の限界

- 自作実装に Lua（`EVAL`）が無いため、「1 コマンドに畳めば解決する」ことを
  スライディングウィンドウで実証できなかった。本物での検証が別途必要である。
- `WATCH` / `MULTI` / `EXEC` による楽観ロック方式を検証していない。
  Lua とは異なるアプローチであり、比較の価値がある。
- 在庫の補償方式について、「補償前にプロセスが落ちる」ケースを実際には再現していない
  （論理的な指摘に留まる）。
- ジョブキューの可視性タイムアウト（処理中リストに残ったジョブをいつ戻すか）を扱っていない。
  実運用では「まだ処理中か、落ちたのか」の判定が必要になる。
- AOF を有効にした状態での書き込み性能を測定していない。
  5.5 の考察は推論であり、実測による裏付けがない。
