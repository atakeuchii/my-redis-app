> **ゴール**: 自作した Redis を「使う側」から見て、各機能が何を解決しているかを体感する。

## Day 1 — キャッシュ

**目標**: キャッシュが何を速くし、何を壊すかを知る。

**やること**
- DB に毎回問い合わせる版を動かし、**レイテンシを測る**
- 素朴なキャッシュ（cache-aside）を入れて改善を測る
- 同時アクセスで**キャッシュスタンピード**を起こす
  - TTL の一斉切れ
  - キャッシュミスの同時多発（サンダリングハード）
- TTL のばらつき、再計算の排他で解決
- 更新時に「キャッシュを消す」か「書き換える」か

**測るもの**
- DB 直撃時と キャッシュ有効時のレイテンシ
- TTL 一斉切れのときの DB へのクエリ数

**深さ**: 標準

## Day 2 — 原子性が壊れる場所

**目標**: 複数コマンドをまたぐと保証が消えることを、2つの形で体験する。

**やること**
- **在庫**: 複数プロセスが同時に `GET` → 判定 → `SET` で在庫を減らす → **売り過ぎる**
- `DECR` の原子性で解決。ただし「在庫 0 で止める」には足りないことに気づく
- **レートリミッタ**: `INCR` + `EXPIRE` の間で落ちると永久ブロック
- `SET NX EX` で解決
- **ジョブキュー**（短く）: `LPOP` + `RPUSH` でジョブが消える → `RPOPLPUSH` が1コマンドである理由

**概念**
- 「原子性の単位はコマンド1個」が、実務の形でどう現れるか
- 未実装のコマンド（`RPOPLPUSH`）が、なぜ1コマンドとして存在するか

**測るもの**
- 並行実行での在庫のずれ
- ジョブの消失数

**深さ**: 標準〜深め（13日間のテーマの集大成）

## Day 3 — ランキング

**目標**: ZSet の span が実用で何を可能にするかを、自分で設計しながら確かめる。

**やること**
- SQL で「自分は何位か」を取り、**10万行での遅さを測る**
- ZSet に載せ替えて比較
- **設計を自分で考える**: 期間別ランキング（日次・週次・累計）をどう持つか。選択肢を列挙して比較
- 「上位10人」と「自分の前後5人」の両方を実装
- 自作版と本物で `ZRANK` の速度を比較

**測るもの**
- SQL の `ORDER BY` + 行番号 vs `ZRANK`
- 要素数を変えたスケーリング

**深さ**: **深め。0から設計を考える日**

## Day 4 — 分散ロック

**目標**: Redis でやってはいけないことを知る。

**やること**
- Day 2 の在庫を、今度は**ロックで**解く
- `SET NX EX` による素朴なロック
- **ロックを取ったまま固まる**（TTL で解放されるが、本人はまだ持っていると思っている）
- 他人のロックを誤って解放する問題 → トークンによる解決（解放も複数コマンドになる問題）
- Redlock の議論と、なぜ etcd / ZooKeeper が別に存在するか
- **Day 2 の「原子的コマンドで解く」との比較**。どちらを選ぶべきか

**測るもの**
- ロック競合時のスループット
- ロック無しとの比較

**深さ**: 標準

## Day 5 — 運用

**目標**: 本番で何を見るか。手順を追うだけでよい。

**やること**
- `SLOWLOG` で遅いコマンドを見つける
- `MEMORY USAGE` / `INFO memory` でメモリを把握
- **パイプライニング**の効果測定（実装編で未実装とした最適化）
- `redis-benchmark` の読み方
- **壊し方**: 接続数の上限、メモリ上限に達したときの挙動、`KEYS *` の影響をアプリ側から観測

**測るもの**
- パイプライン有無のスループット差
- `KEYS *` 実行中の他クライアントのレイテンシ

**深さ**: **浅め。手順を追う**
