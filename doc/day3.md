# Day 3: ランキング機能における Sorted Set の有効性と、期間別ランキングの設計

架空のゲームのスコアランキングを題材に、SQL と Redis Sorted Set を
3 つのアクセスパターンで比較し、期間別ランキングのデータ構造を設計した。

---

## 1. 目的

ランキングは Sorted Set の代表的な用途として挙げられるが、
「どのアクセスパターンで、どの程度有効か」は明示されないことが多い。

本実験では次の 3 点を明らかにする。

1. ランキングの 3 つのアクセスパターン（上位 N 件 / 自分の順位 / 自分の前後）において、
   SQL と ZSet のどちらが有利か
2. その差はどこから生じるか
3. 期間別（日次・週次・累計）ランキングを、限られたコマンドセットでどう設計するか

---

## 2. 実験環境

Day 1・2 と同一。PostgreSQL 16（5437 番）、my-redis（6380 番）、Redis 公式（6379 番）。

データは `plays` 100,000 行（ユーザー 9,995 人、2026 年 9 月の 1 ヶ月間）。
ランキングは「ユーザーごとのベストスコア」で構成した。

SQL 側は 3 水準を比較した。

- **素朴**: 毎回 `plays` を集約する
- **100 万行**: `plays` を 10 倍に複製した場合
- **MV**: マテリアライズドビューで集約結果を事前計算

---

## 3. 結果

### 3.1 SQL の限界

#### 素朴な実装

| クエリ | 10 万行 | 100 万行 |
|---|---|---|
| 上位 20 人 | 69.9 ms | — |
| 自分の順位 | 20.2 ms | 89.0 ms |
| 前後 5 人 | 30.3 ms | — |

実行計画を確認したところ、`idx_plays_score`（score DESC）は使用されず、
`Seq Scan` によって 100,000 行を全件読み取ったのち `HashAggregate` で 9,995 件に集約していた。

```
HashAggregate  (actual time=29.418..31.020 rows=9995)
  Group Key: plays.user_id
  ->  Seq Scan on plays  (actual time=0.010..5.543 rows=100000)
```

**全行を集約するクエリにインデックスは効かない。**
インデックスが有効なのは一部の行を取り出す場合であり、
全件を走査するのであればシーケンシャルスキャンのほうが速いとプランナが判断している。

集約（31 ms）が処理の大半を占め、その後の処理が 3 クエリの差を生んでいた。

| クエリ | 集約後の処理 | 実測 |
|---|---|---|
| 自分の順位 | 9,995 件を走査してカウント | 20.2 ms |
| 前後 5 人 | 9,995 件を全ソート（`row_number()`）→ 11 件取得 | 30.3 ms |
| 上位 20 人 | 9,995 件を全ソート → 20 件取得 → `users` と JOIN | 69.9 ms |

データ量を 10 倍にすると、自分の順位は 4.4 倍に悪化した（20.2 → 89.0 ms）。

#### マテリアライズドビューによる改善

集約結果を事前に保持する方式に変更した。

```sql
CREATE MATERIALIZED VIEW user_best AS
SELECT user_id, max(score) AS best FROM plays GROUP BY user_id;
CREATE INDEX ON user_best(best DESC);
```

| クエリ | 素朴 | MV | 改善率 |
|---|---|---|---|
| 上位 20 人 | 69.9 ms | **0.46 ms** | 152 倍 |
| 自分の順位 | 20.2 ms | **1.45 ms** | 14 倍 |
| 前後 5 人 | 30.3 ms | **5.65 ms** | 5.4 倍 |

**これが SQL 側の最善手であり、ZSet と比較すべきベースラインである。**

### 3.2 ZSet との比較

`ranking:best` に `member = user_id`、`score = ベストスコア` で格納した。

| クエリ | SQL（MV） | ZSet（自作） | ZSet（本物） |
|---|---|---|---|
| 上位 20 人 | **0.46 ms** | 0.575 ms | — |
| 自分の順位 | 1.45 ms | **0.265 ms** | 0.230 ms |
| 前後 5 人 | 5.65 ms | **0.682 ms** | — |

**上位 20 人のみ SQL が勝ち、残る 2 つは ZSet が 5.5 倍・8.3 倍優位であった。**

本実験で唯一、本物の Redis が自作より速かった（0.230 vs 0.265 ms）。
`ZREVRANK` は skiplist の探索を伴うため、サーバ内部の計算が相対的に重く、
C と Clojure の実装差が現れたと考えられる。

### 3.3 更新コスト

| 方式 | 1 人のスコア更新 |
|---|---|
| MV（`REFRESH MATERIALIZED VIEW`） | 20〜30 ms |
| ZSet（`ZADD` 1 回） | 0.3 ms |

MV は部分更新ができず、1 人のスコアが変わっても全件を再集約する。
ZSet は該当メンバーのみを更新できる。

### 3.4 階層判定による往復削減

期間別ランキング（日別・週間・累計）の更新において、
包含関係 **日別 ⊆ 週間 ⊆ 累計** を利用し、狭い範囲から判定して早期に打ち切る方式を実装した。

```
ZSCORE daily → 超えなければ終了（往復 1 回）
ZADD daily + EXPIRE
ZSCORE weekly → 超えなければ終了（往復 3 回）
ZADD weekly + EXPIRE
ZSCORE alltime → 超えなければ終了（往復 5 回）
ZADD alltime（往復 6 回）
```

| 方式 | 1 回の記録 | 往復数 |
|---|---|---|
| 階層判定あり | **0.340 ms** | 平均 2.7（測定条件による） |
| 無条件に 3 回 `ZADD` | 0.930 ms | 常に 3 |

往復数の比は 1.1 倍であるのに対し、実測の差は **2.7 倍**であった。
この乖離の原因は 4.3 で考察する。

なお無条件方式は往復が少ないが、**`ZADD` が無条件に上書きするためベストスコアでなくなる**。
正しさの点で採用できない。

## 4. 考察

### 4.1 「自分の順位」だけが桁違いの差を生む

3 つのクエリで結果が分かれた理由は、計算量の違いにある。

| クエリ | SQL（MV） | ZSet |
|---|---|---|
| 上位 N 件 | O(log N + M) — インデックスの端から M 件 | O(log N + M) |
| 自分の順位 | **O(N)** — 自分より上を数える | **O(log N)** — span の合計 |
| 前後 M 件 | **O(N log N)** — 全ソート後に抽出 | O(log N + M) |

上位 N 件については両者とも同じ計算量であり、
実測で SQL がわずかに勝ったのは Redis へのネットワーク往復（約 0.3 ms）が
B-tree の先頭 20 件の読み取りより重いためである。

これは Day 1 の結論（元の処理が Redis アクセスより軽ければキャッシュの余地がない）と同型である。

自分の順位については、SQL は「自分より上のレコードを数える」以外の方法を持たない。
B-tree に件数を保持する実装（order statistic tree）であれば O(log N) で求まるが、
汎用 RDBMS はそうした構造を採用していない。

一方 ZSet は、skiplist の各ポインタに **span**（最下段で何ノード分を跨ぐか）を保持しており、
探索経路上の span を合計するだけで順位が求まる。

```
Lv2:  header ──(4)──▶ d
Lv1:  header ──(3)──▶ c ──(1)──▶ d
Lv0:  header ─(1)─▶ a ─(1)─▶ b ─(1)─▶ c ─(1)─▶ d
```

`ZRANK c` は `header → c`（span 3）で到達し、合計 3 を得る。
最下段を端から数える必要がない。

### 4.2 スケールしたときの影響

ユーザー数が 10 倍（10 万人）になった場合の予測。

| クエリ | SQL（MV） | ZSet |
|---|---|---|
| 上位 20 人 | ほぼ変わらず（約 0.5 ms） | ほぼ変わらず |
| 自分の順位 | **約 15 ms**（10 倍） | 約 0.3 ms（ほぼ変わらず） |
| 前後 5 人 | **65 ms 超** | ほぼ変わらず |

**SQL は「自分の順位」で破綻し、ZSet は破綻しない。**

実際のゲームでは、ランキング画面に「あなたの順位」が常に表示される。
すなわち **全ユーザーが最も頻繁に呼ぶクエリが、SQL では最も重い**という構造になる。
これが「ランキングには ZSet」と言われる実質的な理由である。

### 4.3 往復数の削減と、高コスト命令の回避

3.4 で往復数の比（1.1 倍）と実測の差（2.7 倍）が乖離した。
原因は、コマンドごとのコストが均一でないことにある。

| コマンド | 内部処理 | 計算量 |
|---|---|---|
| `ZSCORE` | member→score 辞書を 1 回引く | O(1) |
| `ZADD` | 辞書更新 + **skiplist の削除と再挿入** | O(log N) |

既存メンバーの `ZADD` は、skiplist から該当ノードを削除して再挿入する。
1 万要素であれば 7〜8 段のポインタと span を書き換えることになる。

階層判定方式の構造は次のようになっている。

```
階層判定: ZSCORE（安い）× 1〜3 + ZADD（高い）× 0〜3
無条件  : ZADD（高い）× 3
```

**安価な読み取りで判定し、高価な書き込みを回避する**構造であり、
往復数の削減以上の効果を生んでいる。

これは Day 6 で `SINTER` を最小集合から走査した最適化と同型である
（安い判定で候補を絞ってから高い処理を行う）。

### 4.4 期間別ランキングの設計判断

#### 日付をキーに含める

```
ranking:daily:2026-10-04
ranking:weekly:2026-W40
ranking:alltime
```

「日付が変わったらリセットする」のではなく、**日付が変われば別のキーになる**設計とした。

利点は 2 点ある。

- **リセットという操作が不要**。実行漏れや二重実行の心配がない
- **過去のランキングが自然に参照できる**（要件「先週のランキングも見たい」を満たす）

TTL を設定すれば古いデータの削除も Redis に委ねられる（日別 7 日、週間 60 日）。
Day 9 で実装した能動的期限切れが、この削除を担う。

#### 週単位と「直近 N 日間」

当初「週間」を「直近 7 日間」と解釈する案も検討したが、**週単位を採用した**。

両者は実装上まったく異なる性質を持つ。

| | 週単位 | 直近 7 日間 |
|---|---|---|
| 境界 | 固定（月〜日） | **毎日動く** |
| ZSet への直接 `ZADD` | 可能 | **不可能** |

直近 7 日間では、毎日「8 日前のデータを範囲から外す」必要がある。
しかし ZSet に積まれたスコアには「いつのものか」の情報がなく、取り除けない。
TTL はキー単位であり、ZSet の個々のメンバーには設定できない。

したがって**日別 ZSet を 7 つ合成する**（`ZUNIONSTORE ... AGGREGATE MAX`）以外に正確な方法がなく、
合成は 7 万件規模の走査を伴うため、定期実行と結果の保持が必要になる。
これは Day 1 で扱ったキャッシュと同じ構造であり、スタンピード対策も同様に必要となる。

ゲームのランキングにおいては、締め切りが明確なほうがユーザーにも分かりやすく、
週の切り替わりで報酬配布などのイベントを設計できる。
「直近 N 日間」が適するのは SNS のトレンドのように常時変動すべき指標である。

#### 更新か合成か

週間ランキングを「プレイごとに更新する」か「日別から合成する」かの選択については、
**読み書きの比率**が判断基準となる。

| | 書き込みコスト | 読み取りコスト |
|---|---|---|
| 毎回更新 | 3 倍 | 即座 |
| 定期合成 | 1 倍 | 定期的に重い処理 |

ゲームでは「プレイ回数 << ランキング閲覧回数」であるため、
書き込みを増やして読み取りを軽くする前者を採用した。

### 4.5 残る制約

#### ベストスコアの判定が原子的でない

```
ZSCORE daily → 1000
（別プロセスが 2000 を記録）
ZADD daily 1500    ← 2000 を 1500 で上書き
```

Day 2 で扱った read-modify-write の問題がそのまま存在する。

本実験では「1 プレイに数十秒以上かかるため、同一ユーザーの同時更新は起きない」
というドメインの性質を前提として許容した。
連打可能なミニゲームのように同時更新が起こりうる設計では成立しない。

本物の Redis には `ZADD key GT score member`（既存より大きい場合のみ更新）があり、
これを用いれば 1 コマンドで安全に記録できる。自作実装には未実装である。

#### TTL の設定が別コマンド

```
ZADD ranking:daily:2026-10-05 1500 u1
EXPIRE ranking:daily:2026-10-05 604800
```

Day 2 の `INCR` + `EXPIRE` と同じ構造だが、影響は小さい。
TTL が付かなくてもデータ自体は正しく、次の更新時に再設定される。
TTL なしのキーが残るのは「その日に以降誰もプレイしなかった場合」に限られる。

## 5. 結論

1. **ランキングの 3 つのアクセスパターンのうち、ZSet が有効なのは 2 つである。**
   上位 N 件はインデックス付きの SQL で十分であり（0.46 vs 0.575 ms）、
   Redis へのネットワーク往復のぶん不利になる。

2. **「自分の順位」において ZSet は計算量の次元で優位に立つ。**
   SQL が O(N) であるのに対し ZSet は O(log N) であり、
   実測で 5.5 倍、ユーザー数 10 倍の条件では 50 倍の差になると予測される。
   ランキング画面で最も頻繁に呼ばれるクエリがこれであることが、採用の実質的な理由である。

3. **更新の粒度が決定的に異なる。**
   マテリアライズドビューは 1 人のスコア更新に全件再集約（20〜30 ms）を要するのに対し、
   ZSet は `ZADD` 1 回（0.3 ms）で済む。リアルタイム反映が要件なら ZSet 以外の選択肢はない。

4. **期間別ランキングは、日付をキーに含めて TTL に削除を委ねるのが単純である。**
   「リセット」という操作を設計から排除でき、過去分の参照も自然に実現できる。

5. **包含関係のある階層では、狭い範囲から判定することで往復とコストを削減できる。**
   日別 ⊆ 週間 ⊆ 累計 の関係を用い、安価な `ZSCORE` で早期に打ち切ることで、
   無条件更新に対し 2.7 倍の性能差を得た。

6. **ただし、ベストスコアの判定は原子的でない。**
   本実験はドメインの性質（同一ユーザーの同時プレイが起きない）を前提として許容した。
   厳密さが必要なら `ZADD GT` または Lua が必要である。

## 6. 本実験の限界

- 往復数の計測において、1 人あたりのプレイ回数が少ない条件で測定したため、
  階層判定による削減効果を十分に示せていない（平均 2.7 往復に留まった）。
  実際のゲームに近い条件（1 人が多数回プレイする）での再測定が必要である。
- ユーザー数を 10 倍にした場合の ZSet の性能を実測していない。
  4.2 の予測は計算量からの推論である。
- `ZADD GT` および Lua スクリプトによる原子的な記録を本物の Redis で検証していない。
- 直近 N 日間ランキングの合成コストを実測していない。
  「重い」という判断は要素数からの推論である。
- ZSet のメモリ使用量を測定していない。
  1 万件 × 日数分のキーを保持する場合のメモリ影響は未評価である。
