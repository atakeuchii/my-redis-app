# Day 4: Redis による分散ロックの保証範囲と、その適用可否

Day 2 で原子的コマンドによって解いた在庫問題を、今度はロックで解き直し、
さらにバッチ処理の排他制御を題材として、Redis による分散ロックの限界を計測した。

---

## 1. 目的

`SET NX EX` による分散ロックは Redis の代表的な用途として紹介されるが、
その保証範囲と前提条件は十分に明示されないことが多い。

本実験では次の 4 点を明らかにする。

1. ロックで解決できる問題と、できない問題の境界
2. `SET NX EX` 方式が破れる条件と、その再現
3. トークンによる改善が何を直し、何を直さないか
4. 他のロック機構と比較したときの Redis の位置づけ

---

## 2. 実験環境

Day 1〜3 と同一。PostgreSQL 16（5437 番）、my-redis（6380 番）、Redis 公式（6379 番）。

題材は 2 つ用いた。

- **在庫 + 購入履歴**: Redis の在庫と PostgreSQL の履歴テーブルを同時に更新する
- **バッチ処理の排他**: 複数ワーカーのうち 1 台だけが集計処理を実行する

---

## 3. 結果

### 3.1 ロックで解決できない問題 — 2 つのリソースをまたぐ更新

#### 素朴な実装

Redis の在庫を減らし、PostgreSQL に購入履歴を記録する処理を実装した。

在庫 20 個に対し 20 スレッドから 200 回の購入を試行した結果、
**履歴が 91〜108 件**記録され、売り過ぎが発生した。

#### `DECR` による部分的な解決

Day 2 と同様に `DECR` で在庫を原子的に減らしたところ、売り過ぎは解消し、
在庫の減少数と履歴の件数が一致した。

#### クラッシュ時の不整合

`DECR` の後、`INSERT` の前に 30% の確率でクラッシュする条件で実行した。

| 試行 | 在庫の減少 | 履歴 | 差 |
|---|---|---|---|
| 1〜3 回目 | — | — | **4〜11 件** |

**在庫は減ったが履歴が存在しない**状態が発生した。
`DECR` が保証するのは「在庫を減らしすぎない」ことのみであり、
Redis と DB という 2 つのリソースの整合性は保証しない。

#### ロックを追加しても解決しない

ロックは「他プロセスによる割り込み」を防ぐが、「自プロセスの途中終了」は防げない。

```
ロックあり:
  A がロック取得 → DECR → クラッシュ（INSERT の前）
  → ロックは TTL で解放される
  → しかし在庫は減ったまま、履歴は無い
```

**ロックは排他の道具であり、原子性（all-or-nothing）の道具ではない。**

#### DB のトランザクションによる解決

```clojure
(jdbc/with-transaction [tx db/ds]
  (let [n (update "UPDATE items SET stock = stock - 1 WHERE item_id = ? AND stock > 0")]
    (if (pos? n)
      (insert "INSERT INTO purchases ...")
      :sold-out)))
```

同一トランザクション内に 2 つの操作を収めることで、
同時実行（行ロックによる直列化）とクラッシュ（ロールバック）の両方が解決した。

**Redis を使わないことが、この題材における正解であった。**

### 3.2 ロックが必要な場面 — バッチ処理の排他

複数のアプリサーバのうち 1 台だけが集計バッチを実行する、という要件を題材とした。
これは DB のトランザクションでは解決できない（複数プロセスに跨るため）。

#### 素朴なロック

```clojure
(if (= "OK" (r/cmd pool "SET" lock-key "1" "NX" "EX" ttl))
  (try (f) (finally (r/cmd pool "DEL" lock-key)))
  :skipped)
```

TTL が処理時間より十分長い条件（TTL 10 秒、処理 100 ms）では、
20 ワーカーのうち 1 台のみが実行し、正しく動作した。

#### TTL 切れによる重複実行

TTL 1 秒、処理 3000 ms、ロックが取れるまで待つ 5 ワーカーの条件で実行した。

```
worker 0:     0 〜 3000 ms
worker 1:  1050 〜 4050 ms     ← 0 がまだ実行中
worker 2:  2100 〜 5100 ms     ← 0 と 1 がまだ実行中
```

**相互排他が破れ、最大 3 ワーカーが同時に実行された。**

このとき 2 つの問題が同時に発生している。

1. TTL 切れ後も前の保持者が処理を続けている（相互排他の破れ）
2. 前の保持者が完了時に `DEL` を実行し、**次の保持者のロックを削除している**

#### 処理時間が予測できない場合

TTL 5 秒、通常の処理時間 1000 ms という余裕のある設定でも、
40% の確率で 8 秒の停止（GC 停止やスワップを模擬）を挿入したところ、重複実行が発生した。

**処理時間の上限が保証できない以上、安全な TTL は存在しない。**

### 3.3 トークンによる改善

ロックの値に一意なトークンを格納し、解放時に自分のものか確認する方式を実装した。

```clojure
(defn- release-lock! [pool token]
  (when (= token (r/cmd pool "GET" lock-key))
    (r/cmd pool "DEL" lock-key)))
```

ロックが空になった回数を計測した（TTL 1 秒、処理 3000 ms、5 ワーカー、3 回試行）。

| 方式 | ロックが空になった回数 |
|---|---|
| トークンなし | 5 回 |
| トークンあり | **3〜4 回** |

トークンなしでは、TTL 切れに加えて「他人による `DEL`」でもロックが空になる。
トークンありでは TTL 切れのみとなり、回数が減少した。

**ただし重複実行自体は解消していない。**

#### 解放処理も原子的でない

```clojure
(r/cmd pool "GET" lock-key)   ; ① 自分のものか確認
(r/cmd pool "DEL" lock-key)   ; ② 削除
```

①と②の間に TTL 切れと他者の取得が発生すれば、やはり他人のロックを削除する。
確率は低いが（数百マイクロ秒の窓）、ゼロではない。

本物の Redis では Lua スクリプトにより 1 コマンド化できることを確認した。

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0
end
```

自作実装では Lua が未実装のため、代替案として
**「解放せず TTL に任せる」**方式が現実的であることを確認した。
毎時バッチであれば TTL を 55 分とし、解放処理を行わなければ誤削除は発生しない。

## 4. 考察

### 4.1 トークンが解決する問題の範囲

| 問題 | トークンで直るか |
|---|---|
| 他人のロックを削除する | **直る** |
| TTL 切れ後も処理が続く（重複実行） | 直らない |
| 死んだプロセスのロックが残る | 直らない（TTL の役目） |

トークンなしの場合、誤削除が連鎖的な悪化を引き起こす。

```
A がロック取得 → TTL 切れ → B が取得
A が完了して B のロックを DEL   ← ロックが空になる
C が取得（B がまだ実行中）       ← 本来より早く入れてしまう
```

**誤削除は「次の保持者が本来より早く入れる」ことを引き起こし、重複をさらに増やす。**
計測で 5 回 → 3〜4 回に減少したのは、この連鎖が止まったためである。

したがってトークンの効果は「重複を無くす」ことではなく、
**「TTL を適切に設定できている場合に、誤削除による想定外の破れを防ぐ」**ことである。

### 4.2 TTL 方式の本質的な限界

ロックの解放機構で分類すると、Redis の位置づけが明確になる。

| 種類 | 解放の契機 | 例 |
|---|---|---|
| 接続に紐づく | 接続が切れたら自動解放 | DB の行ロック、`pg_advisory_lock` |
| **リースに紐づく** | **時間切れで自動解放** | **Redis の `SET NX EX`** |
| セッションに紐づく | ハートビート途絶で解放 | ZooKeeper の ephemeral node |

**Redis がリース型であることが、本実験で観測した問題の根源である。**

リース型は「生きているかどうかを時間で推測する」方式であり、本質的に不正確である。

```
TTL 10 秒 = 「10 秒経ったら死んだとみなす」
→ 死んでいなくても死んだとみなす（重複実行）
→ 死んでいても 10 秒は生きているとみなす（無駄な待機）
```

対して PostgreSQL のアドバイザリロックは TTL を持たない。
DB サーバが TCP 接続を監視しており、クライアントが落ちれば接続断を検知して自動解放するためである。
**「生きているか」を推測ではなく観測している。**

ただし接続監視にも限界がある。GC 停止中のプロセスは TCP 接続を維持したまま何もしていないため、
接続監視では検知できない。**GC 停止はどのロック機構でも防げない。**

### 4.3 用途別の選択

本実験と Day 2・Day 3 の結果を統合すると、次の判断が導かれる。

#### 在庫・残高・カウンタ

| 条件 | 選ぶもの |
|---|---|
| DB だけで完結する | **DB のトランザクション**（条件付き `UPDATE`） |
| 履歴も同時に記録する | 同上（同一トランザクション内） |
| 極端に高頻度 | Redis + Lua。ただし DB との整合は別途設計 |

**ロックは使わない。** 条件付き更新で足りる。

#### バッチ処理の重複実行防止

| 条件 | 選ぶもの |
|---|---|
| 重複しても冪等 | **Redis の `SET NX EX`** で十分 |
| 重複すると困る（課金、メール送信） | DB のアドバイザリロック、ジョブスケジューラ |
| Kubernetes 上 | **CronJob の `concurrencyPolicy: Forbid`** |

インフラ層で解決できるなら、アプリでロックを書かない。

#### 重い計算の重複排除

Day 1 のランキング再計算が該当する。**Redis の `SET NX EX` が適切**である。
重複しても結果は同じであり、無駄な計算が走るだけである。

#### 外部 API の二重呼び出し防止

**ロックでは解決しない。** ロック取得後、API 呼び出し中にプロセスが落ちると
「呼んだか呼んでいないか」が判定できない。

正しい形は DB に状態を記録してトランザクションで守るか、
API 側の冪等キーを利用することである。

#### 複数システムに跨る更新

**ロックでは解決しない。** 3.1 で確認した通りである。
Saga パターン（補償トランザクション）か Outbox パターン、
あるいは「1 つのリソースにまとめる」設計変更が必要となる。

## 5. 結論

1. **ロックは排他の道具であり、原子性の道具ではない。**
   複数リソースをまたぐ更新において、ロックを追加しても
   「自プロセスの途中終了による不整合」は解決しない。

2. **Redis のロックはリース型（TTL 依存）であり、安全な TTL は原理的に存在しない。**
   処理時間の上限が保証できない限り、TTL 切れによる重複実行は避けられない。
   実測では TTL 1 秒・処理 3 秒の条件で 3 ワーカーが同時実行された。

3. **トークンは誤削除を防ぐが、重複実行は防がない。**
   効果は「TTL が適切な場合に、想定外の破れを防ぐ」ことに限られる。
   誤削除による連鎖的な悪化を止める意味で、導入する価値はある。

4. **解放処理も原子的でなく、Lua なしでは完全に正しく実装できない。**
   代替として「解放せず TTL に任せる」方式が、バッチ処理では現実的である。

5. **「効率のため」か「正しさのため」かで選択が分かれる。**
   効率のためなら Redis で十分。正しさのためなら Redis では不十分であり、
   フェンシングトークンを持つ合意システム（etcd / ZooKeeper）が必要となる。

6. **ロックを使う前に、原子的な操作で済まないかを検討すべきである。**
   本実験の在庫問題は、DB のトランザクションで完全に解決した。
   Redis のロックが適切だったのは、Day 1 の「重い計算の重複排除」のみであった。

## 6. 本実験の限界

- Redlock を実装・検証していない。4.4 の議論は文献に基づくものである。
- フェンシングトークンによる解法を実装していない。
- PostgreSQL のアドバイザリロック（`pg_try_advisory_xact_lock`）の動作を
  概念的に説明したのみで、実測による比較を行っていない。
- GC 停止を `Thread/sleep` で模擬したが、実際の GC 停止とは挙動が異なる
  （実際の GC は全スレッドを停止させる）。
- ロック取得時の待機戦略（ポーリング間隔、タイムアウト）を最適化していない。
  50 ms 間隔の固定ポーリングであり、競合時の挙動は改善の余地がある。
- Redis Cluster 環境での挙動を検証していない。
